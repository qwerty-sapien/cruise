# Narrow skill activation

Apply the smallest skill that matches the current boundary. Do not load a broad workflow merely because its subject appears in ordinary engineering work.

- `seeking-alpha`: use only for explicit novelty, research-edge, or non-obvious edge search. Do not activate for ordinary implementation, bug fixing, or deterministic optimization with a known objective.
- `dag-prompts`: use only for an explicit DAG or preregistration request, or at least three independently dispatchable units. Use a linear checklist for ordinary one- or two-step work.
- `auto-experiment`: use only for an actual experiment, model comparison, statistical claim, protected outcome, or holdout decision. Exploratory code without those boundaries stays local.
- `ship-kaggle-kernels`: use only at packaging, certification, launch, submission, or remote-monitoring boundaries. Do not activate while editing unrelated training code.
- `noconflict-env`: start with the exact failing command, interpreter, and dependency. Expand to an environment inventory only after evidence of a compatibility conflict.
- `appi-enforcement`: obey `NONE`, `AFFECTED_SCOPE`, or `FULL`. Passing affected checks never triggers unconditional recursive Cruise debug; expand only for a failing or ambiguous affected behavior.

These boundaries reduce repeated unaffected work without weakening scientific, privacy, security, release, or human-gate controls.
